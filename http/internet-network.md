# 인터넷 네트워크

### 인터넷 통신의 전제
- 클라이언트와 서버가 물리적으로 직접 연결되는 경우는 거의 없으며, 수많은 중간 노드(라우터, 스위치)를 거치는 인터넷 망을 통과함
- 따라서 어느 경로로 어느 대상에게 보낼 것인지를 규정하는 규칙, 즉 프로토콜이 반드시 필요함

<br>

### IP(Internet Protocol)
- 인터넷 계층의 프로토콜로써, 인터넷 통신의 최소 기반이라 할 수 있음
- 역할
  - 지정한 IP 주소(IP Address)로 데이터를 전달함
  - 패킷(Packet)이라는 통신 단위로 데이터를 전달함
- IP 패킷의 구성
  - 헤더: 출발지 IP, 목적지 IP, 기타 정보가 들어감
  - 페이로드: 실제 전송할 데이터가 들어감
- 동작 흐름
  1. 클라이언트가 출발지/목적지 IP를 담은 패킷을 생성함
  2. 중간 노드들이 목적지 IP를 보고 다음 노드로 전달함(라우팅)
  3. 서버에 도착한 후, 서버도 동일한 방식으로 응답 패킷을 전송함

<br>

### IP 프로토콜의 한계
- 비연결성: 수신 대상이 없거나 서비스 불능 상태여도 그대로 패킷을 전송함
- 비신뢰성: 중간 노드 장애로 패킷이 소실되어도 송신 측에서 인지할 수 없으며, 패킷이 분할 전송되는 과정에서 도착 순서가 뒤바뀔 수 있음
- 프로그램 구분 불가: 같은 IP를 사용하는 서버에서 통신 애플리케이션이 둘 이상인 경우 이를 구분할 수 없음
- 위 한계를 보완하기 위해 상위 계층인 전송 계층(TCP)이 필요함

<br>

### 인터넷 프로토콜 스택의 4계층
- 애플리케이션 계층: 메시지를 생성하는 계층. HTTP, FTP 등이 해당됨
- 전송 계층: 포트, 전송 제어, 순서, 검증을 담당하는 계층. TCP, UDP가 해당됨
- 인터넷 계층: 출발지/목적지 주소 지정과 라우팅을 담당하는 계층. IP가 해당됨
- 네트워크 인터페이스 계층: LAN 카드, LAN 드라이버를 통한 물리적 전송을 담당하는 계층. Ethernet 등이 해당됨
- 데이터 생성 및 전달 순서
  1. 애플리케이션(웹 브라우저 등)에서 메시지를 생성함
  2. SOCKET 라이브러리를 통해 OS 계층으로 전달함
  3. TCP 정보를 생성한 후 메시지 데이터를 포함시킴 -> TCP 세그먼트
  4. IP 패킷을 생성한 후 TCP 데이터를 포함시킴 -> IP 패킷
  5. LAN 카드를 통해 Ethernet frame 형태로 물리 전송함
- 결과적으로 HTTP -> TCP -> IP -> Ethernet frame 순으로 캡슐화가 이루어짐

<br>

### TCP(Transmission Control Protocol, 전송 제어 프로토콜)
- TCP/IP 패킷 구조
```
IP 패킷
 ├─ 출발지 IP, 목적지 IP, 기타...
 └─ TCP 세그먼트
     ├─ 출발지 PORT, 목적지 PORT
     ├─ 전송 제어, 순서, 검증 정보...
     └─ 전송 데이터
```
- 특징
  - 연결지향: TCP 3 way handshake를 통해 연결을 맺음. 물리적 연결이 아닌 논리적/가상 연결임
  - 데이터 전달 보증: 수신 측이 수신 사실을 응답해줌
  - 순서 보장: 순서가 어긋나면 어긋난 지점부터 재전송을 요청함
  - 위와 같은 특성으로 인해 신뢰할 수 있는 프로토콜로 분류되며, 현재 대부분의 통신이 TCP 기반으로 이루어짐
- TCP 3 way handshake 절차
  1. 클라이언트가 서버로 SYN을 전송함(접속 요청)
  2. 서버가 클라이언트로 SYN + ACK를 전송함(요청 수락 + 접속 요청)
  3. 클라이언트가 서버로 ACK를 전송함(요청 수락)
  4. 연결이 성립된 후 데이터를 전송함
  - 3단계에서 ACK를 전송할 때 데이터를 함께 실어 보내는 것도 가능함
- 순서 보장 동작 예시
  1. 패킷1, 패킷2, 패킷3 순서로 전송함
  2. 패킷1, 패킷3, 패킷2 순서로 도착함
  3. 서버가 패킷2부터 다시 보내달라고 요청함

<br>

### UDP(User Datagram Protocol, 사용자 데이터그램 프로토콜)
- 기능이 거의 없는 단순한 프로토콜로써, 하얀 도화지에 비유할 수 있음
- 연결지향이 아니므로 3 way handshake를 수행하지 않으며, 데이터 전달 보증과 순서 보장도 하지 않음
- 대신 단순하고 빠름
- 정리하면 IP와 거의 동일하며, PORT와 체크섬 정도만 추가된 형태라 볼 수 있음
- 신뢰성이 필요한 경우, 애플리케이션 레벨에서 직접 구현해야 함
- HTTP/3가 UDP 기반으로 설계되면서 최근 다시 주목받고 있음

<br>

### PORT
- 같은 IP 내에서 동작하는 여러 프로세스(애플리케이션)를 구분하기 위해 사용하는 번호
- IP를 목적지 아파트, PORT를 몇 호에 해당하는 개념으로 이해할 수 있음
- TCP/IP 패킷에는 출발지 IP/PORT와 목적지 IP/PORT가 모두 포함됨
- 0 ~ 65535까지 할당 가능하며, 0 ~ 1023은 잘 알려진 포트(Well-known Port)이므로 임의 사용을 지양해야 함
  - ex. FTP: 20, 21 / TELNET: 23 / HTTP: 80 / HTTPS: 443
- 포트 범위에 대한 상세한 내용은 [HTTP Client](/http/http-client.md) 참고

<br>

### DNS(Domain Name System)
- IP 주소만 사용할 때의 문제
  - IP는 사람이 기억하기 어려움
  - IP는 변경될 수 있으며, 변경되면 기존 주소로 접근할 수 없음
- 전화번호부와 같은 개념으로써, 도메인 명을 IP 주소로 변환해주는 역할을 수행함
- 사용 흐름
  1. 클라이언트가 DNS 서버에 도메인 명을 질의함(ex. google.com)
  2. DNS 서버가 매핑된 IP 주소를 응답함(ex. 200.200.200.2)
  3. 클라이언트가 해당 IP로 접속함
- IP 주소 체계, 도메인 표기 규칙, DDNS에 대한 상세한 내용은 [HTTP Client](/http/http-client.md) 참고

<br>

### 정리
- IP: 목적지에 패킷을 전달하는 최소 기능만 제공하며, 비연결성과 비신뢰성을 가짐
- TCP: 연결, 전달 보증, 순서 보장을 더한 신뢰성 프로토콜
- UDP: IP + PORT + 체크섬 수준의 단순하고 빠른 프로토콜
- PORT: 같은 IP 내에서의 프로세스 구분
- DNS: 도메인 명과 IP 주소 간 변환

#### 배워가는 것들
- HTTP를 이해하려면 그 아래에 깔려있는 IP, TCP, PORT, DNS를 먼저 알아야 한다는 것을 알게 되었다. HTTP의 특성 상당수가 결국 하위 계층의 한계를 보완하는 과정에서 나온 결과였다
- IP의 세가지 한계(비연결성, 비신뢰성, 프로그램 구분 불가)를 TCP가 어떻게 메우는지 흐름으로 익힐 수 있었다. 장애 상황을 분석할 때 어느 계층의 문제인지 나누어 볼 수 있는 기준이 된다고 생각한다
