# HTTP 캐시와 조건부 요청

### 캐시가 없을 때의 문제
- 첫 번째 요청에서 1.1M을 전송하고(HTTP 헤더 0.1M + HTTP 바디 1.0M 가정), 두 번째 요청에서도 데이터가 동일함에도 다시 1.1M을 전송하게 됨
- 데이터가 변경되지 않아도 계속 네트워크를 통해 데이터를 다운로드해야 함
- 인터넷 네트워크는 매우 느리고 비쌈
- 브라우저 로딩 속도가 느려지므로, 결과적으로 느린 사용자 경험을 제공하게 됨

<br>

### 캐시 적용
- 첫 번째 요청
```http
HTTP/1.1 200 OK
Content-Type: image/jpeg
cache-control: max-age=60
Content-Length: 34012
```
  - cache-control: max-age=60은 캐시가 유효한 시간(초)을 의미함
  - 응답 결과를 브라우저 캐시에 저장하며, 60초 동안 유효함
- 두 번째 요청(캐시 유효 시간 내)
  - 캐시 유효 시간을 검증한 후, 유효하므로 네트워크 사용 없이 캐시에서 조회함
  - 캐시 가능 시간 동안 네트워크를 사용하지 않아도 되므로, 비싼 네트워크 사용량을 절감하고 브라우저 로딩 속도를 크게 높일 수 있음
- 세 번째 요청(캐시 시간 초과)
  - 캐시 유효 시간이 초과하면 서버를 통해 데이터를 다시 조회하고 캐시를 갱신함
  - 이때 다시 네트워크 다운로드가 발생함

<br>

### 검증 헤더와 조건부 요청 1 - Last-Modified
- 문제 인식
  - 캐시 유효 시간이 초과해서 서버에 다시 요청할 때는 두가지 상황이 존재함
    1. 서버에서 기존 데이터를 변경한 경우
    2. 서버에서 기존 데이터를 변경하지 않은 경우
  - 2번의 경우 데이터를 다시 전송하는 대신 저장해 둔 캐시를 재사용할 수 있음
  - 단, 클라이언트의 데이터와 서버의 데이터가 같다는 사실을 확인할 방법이 필요함
- 첫 번째 요청
```http
HTTP/1.1 200 OK
Content-Type: image/jpeg
cache-control: max-age=60
Last-Modified: 2020년 11월 10일 10:00:00
Content-Length: 34012
```
  - 데이터의 최종 수정일을 캐시와 함께 저장함
- 두 번째 요청(캐시 시간 초과)
```http
GET /star.jpg
if-modified-since: 2020년 11월 10일 10:00:00
```
  - 캐시가 보유한 최종 수정일을 조건부 요청 헤더로 전송함
- 서버의 데이터가 수정되지 않은 경우의 응답
```http
HTTP/1.1 304 Not Modified
Content-Type: image/jpeg
cache-control: max-age=60
Last-Modified: 2020년 11월 10일 10:00:00
Content-Length: 34012
```
  - HTTP Body가 없으므로 헤더인 0.1M만 전송됨
  - 클라이언트는 응답 결과를 재사용하고 헤더 데이터를 갱신함
  - 캐시가 다시 60초 동안 유효한 상태가 되며, 이후에는 캐시에서 조회함
- 정리
  - 캐시 유효 시간이 초과해도 서버의 데이터가 갱신되지 않았으면, 304 Not Modified와 헤더 메타 정보만 응답함(바디 없음)
  - 클라이언트는 서버가 보낸 응답 헤더 정보로 캐시의 메타 정보를 갱신하고, 캐시에 저장된 데이터를 재활용함
  - 결과적으로 네트워크 다운로드는 발생하지만 용량이 적은 헤더 정보만 다운로드하게 되므로 매우 실용적인 해결책임
- 수치 비교 예시
  - 데이터 미변경(캐시 10:00:00 = 서버 10:00:00): 304 Not Modified와 헤더만 전송하므로 0.1M
  - 데이터 변경(캐시 10:00:00 vs 서버 11:00:00): 200 OK와 전체 데이터를 전송하므로 1.1M(헤더 0.1M + 바디 1.0M)

<br>

### 검증 헤더와 조건부 요청 2 - ETag
- 용어 정리
  - 검증 헤더: 캐시 데이터와 서버 데이터가 같은지 검증하는 데이터. Last-Modified, ETag가 해당됨
  - 조건부 요청 헤더: 검증 헤더로 조건에 따른 분기를 수행함. If-Modified-Since(Last-Modified 사용), If-None-Match(ETag 사용)가 해당됨
  - 조건이 만족하면 200 OK로 전체 데이터를 전송하고, 만족하지 않으면 304 Not Modified로 헤더만 전송함
- Last-Modified와 If-Modified-Since의 단점
  - 1초 미만(0.x초) 단위로 캐시를 조정할 수 없음
  - 날짜 기반의 로직만 사용 가능함
  - 데이터를 수정해서 날짜는 달라졌지만 실제 데이터 결과는 똑같은 경우에 대응할 수 없음
  - 서버에서 별도의 캐시 로직을 관리하고 싶은 경우에 대응할 수 없음(ex. 스페이스나 주석처럼 영향이 거의 없는 변경에서 캐시를 유지하고 싶은 경우)
- ETag(Entity Tag)
  - 캐시용 데이터에 임의의 고유한 버전 이름을 부여함(ex. ETag: "v1.0", ETag: "a2jiodwjekjl3")
  - 데이터가 변경되면 이 이름을 변경함(Hash를 다시 생성함. ex. ETag: "aaaaa" -> ETag: "bbbbb")
  - 단순하게 ETag만 보내서 같으면 유지하고 다르면 다시 받는 구조임
- 첫 번째 요청
```http
HTTP/1.1 200 OK
Content-Type: image/jpeg
cache-control: max-age=60
ETag: "aaaaaaaaaa"
Content-Length: 34012
```
- 두 번째 요청(캐시 시간 초과)
```http
GET /star.jpg
If-None-Match: "aaaaaaaaaa"
```
- 서버의 데이터가 수정되지 않은 경우의 응답
```http
HTTP/1.1 304 Not Modified
Content-Type: image/jpeg
cache-control: max-age=60
ETag: "aaaaaaaaaa"
Content-Length: 34012
```
  - HTTP Body가 없으므로 0.1M만 전송되며, 응답 결과를 재사용하고 헤더 데이터를 갱신함
- 정리
  - 캐시 제어 로직을 서버에서 완전히 관리함
  - 클라이언트는 단순히 이 값을 서버에 제공할 뿐이며, 캐시 메커니즘을 알지 못함
  - 활용 예시
    - 서버는 베타 오픈 기간인 3일 동안 파일이 변경되어도 ETag를 동일하게 유지할 수 있음
    - 애플리케이션 배포 주기에 맞추어 ETag를 모두 갱신할 수 있음

<br>

### 캐시와 조건부 요청 헤더 총정리
- 캐시 제어 헤더
  - Cache-Control: 캐시를 제어함
  - Pragma: 캐시를 제어함(하위 호환용)
  - Expires: 캐시 유효 기간을 지정함(하위 호환용)
- Cache-Control 주요 지시어
  - max-age: 캐시 유효 시간을 초 단위로 지정함
  - no-cache: 데이터는 캐시해도 되지만, 항상 원(origin) 서버에 검증하고 사용해야 함
  - no-store: 데이터에 민감한 정보가 있으므로 저장하면 안 됨(메모리에서 사용하고 최대한 빨리 삭제해야 함)
- Pragma
  - ex. Pragma: no-cache
  - HTTP 1.0 하위 호환용으로 사용함
- Expires
  - ex. expires: Mon, 01 Jan 1990 00:00:00 GMT
  - 캐시 만료일을 정확한 날짜로 지정하며, HTTP 1.0부터 사용함
  - 지금은 더 유연한 Cache-Control: max-age 사용을 권장하며, 함께 사용하면 Expires는 무시됨
- 검증 헤더(Validator): ETag, Last-Modified
- 조건부 요청 헤더
  - If-Match, If-None-Match: ETag 값을 사용함
  - If-Modified-Since, If-Unmodified-Since: Last-Modified 값을 사용함

### 프록시 캐시
- 원 서버에 직접 접근할 때의 문제
  - 미국에 있는 원(origin) 서버에 한국 클라이언트가 직접 접근하면 500ms(0.5초)가 소요됨
- 프록시 캐시 도입
  - 한국 어딘가에 프록시 캐시 서버를 두는 구조를 사용함
  - 첫 번째 요청에서는 프록시 캐시 서버가 원 서버로부터 400ms에 데이터를 받아옴
  - 이후 클라이언트는 프록시 캐시 서버로부터 100ms(0.1초)에 응답을 수신함
  - CDN 등이 이러한 구조에 해당함
- public 캐시와 private 캐시
  - public 캐시: 프록시 캐시 서버 등 여러 사용자가 공유하는 캐시
  - private 캐시: 웹 브라우저 등 개별 사용자의 로컬 캐시
- Cache-Control 기타 지시어
  - public: 응답이 public 캐시에 저장되어도 됨
  - private: 응답이 해당 사용자만을 위한 것이므로 private 캐시에 저장해야 함(기본값)
  - s-maxage: 프록시 캐시에만 적용되는 max-age
  - Age: 오리진 서버에서 응답한 후 프록시 캐시 내에 머문 시간을 초 단위로 나타내는 응답 헤더(ex. Age: 60)

<br>

### 캐시 무효화
- 확실한 캐시 무효화 응답
```
Cache-Control: no-cache, no-store, must-revalidate
Pragma: no-cache
```
  - Pragma는 HTTP 1.0 하위 호환용임
  - 캐시를 적용하지 않아도 웹 브라우저가 임의로 캐시할 수 있으므로, 확실히 무효화하려면 위 지시어를 모두 넣어야 함
- 지시어별 의미
  - no-cache: 데이터는 캐시해도 되지만 항상 원 서버에 검증하고 사용해야 함(이름과 의미가 다르므로 주의)
  - no-store: 데이터에 민감한 정보가 있으므로 저장하면 안 됨(메모리에서 사용하고 최대한 빨리 삭제해야 함)
  - must-revalidate: 캐시 만료 후 최초 조회 시 원 서버에 검증해야 하며, 원 서버 접근 실패 시 반드시 오류가 발생해야 함(504 Gateway Timeout). 캐시 유효 시간 이내라면 캐시를 사용함
- no-cache의 기본 동작(정상 상황)
  1. 웹 브라우저가 프록시 캐시에 요청함(no-cache + ETag)
  2. 프록시 캐시가 원 서버에 요청함(no-cache + ETag)
  3. 원 서버에서 검증을 수행함
  4. 원 서버가 프록시 캐시로 304 Not Modified를 응답함
  5. 프록시 캐시가 웹 브라우저로 304 Not Modified를 응답함
  6. 웹 브라우저가 캐시 데이터를 사용함
- no-cache와 must-revalidate의 차이 - 원 서버 접근이 불가능한 경우
  - no-cache: 프록시 캐시가 원 서버에 접근할 수 없는 경우, 캐시 서버 설정에 따라 캐시 데이터를 반환할 수 있음(Error 또는 200 OK). 오류보다는 오래된 데이터라도 보여주는 편이 낫다는 관점임
  - must-revalidate: 원 서버에 접근할 수 없는 경우 항상 오류가 발생해야 함(504 Gateway Timeout). 통장 잔고처럼 돈과 관련된 매우 중요한 결과라면 오래된 데이터를 보여주면 안 된다는 관점임

#### 배워가는 것들
- 캐시가 단순히 저장하고 재사용하는 기능이 아니라, 검증 헤더와 조건부 요청을 통해 만료 이후에도 데이터를 재사용할 수 있는 구조라는 점을 알게 되었다
- no-cache라는 이름과 실제 동작(캐시는 하되 항상 검증함)이 다르다는 점을 확실히 정리할 수 있었다. 저장 자체를 막으려면 no-store를 사용해야 한다
- must-revalidate와 no-cache의 차이가 원 서버 접근 실패 시의 동작에 있다는 점이 인상적이었다. 금액처럼 정확성이 중요한 데이터라면 오래된 캐시를 보여주는 것보다 오류를 내는 편이 낫다는 판단 기준을 얻었다
