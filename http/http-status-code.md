# HTTP 상태코드

### 상태 코드의 분류
- 클라이언트가 보낸 요청의 처리 상태를 응답에서 알려주는 기능
  - 1xx(Informational): 요청이 수신되어 처리 중임
  - 2xx(Successful): 요청이 정상적으로 처리됨
  - 3xx(Redirection): 요청을 완료하려면 추가 행동이 필요함
  - 4xx(Client Error): 클라이언트 오류. 잘못된 문법 등으로 서버가 요청을 수행할 수 없음
  - 5xx(Server Error): 서버 오류. 서버가 정상적인 요청을 처리하지 못함
- 모르는 상태 코드가 나타나는 경우
  - 클라이언트가 인식할 수 없는 상태코드를 서버가 반환하면, 클라이언트는 상위 상태코드로 해석해서 처리함
    - 299 -> 2xx(Successful)로 해석함
    - 451 -> 4xx(Client Error)로 해석함
    - 599 -> 5xx(Server Error)로 해석함
  - 덕분에 미래에 새로운 상태 코드가 추가되어도 클라이언트를 변경하지 않아도 되는 구조를 가짐
- 1xx는 거의 사용하지 않으므로 실무 학습에서는 생략 가능함

<br>

### 2xx - 성공
- 200 OK: 요청이 성공함
- 201 Created: 요청이 성공해서 새로운 리소스가 생성됨
  - 생성된 리소스는 응답의 Location 헤더 필드로 식별함(ex. Location: /members/100)
- 202 Accepted: 요청이 접수되었으나 처리가 완료되지 않았음
  - 배치 처리 같은 곳에서 사용함(ex. 요청 접수 후 1시간 뒤에 배치 프로세스가 요청을 처리하는 경우)
- 204 No Content: 요청을 성공적으로 수행했지만 응답 페이로드 본문에 보낼 데이터가 없음
  - ex. 웹 문서 편집기에서의 save 버튼. save 결과로 아무 내용이 없어도 무방하며, save 버튼을 눌러도 같은 화면을 유지해야 함. 결과 내용이 없어도 204 메시지(2xx)만으로 성공을 인식할 수 있음

<br>

### 3xx - 리다이렉션
- 300 Multiple Choices: 사용하지 않음
- 301 Moved Permanently: 영구 리다이렉션
- 302 Found: 일시 리다이렉션
- 303 See Other: 일시 리다이렉션
- 304 Not Modified: 특수 리다이렉션(캐시)
- 307 Temporary Redirect: 일시 리다이렉션
- 308 Permanent Redirect: 영구 리다이렉션
- 리다이렉션의 기본 동작
  - 웹 브라우저는 3xx 응답 결과에 Location 헤더가 있으면 해당 위치로 자동 이동함(리다이렉트)
  - 자동 리다이렉트 흐름
    1. 클라이언트가 GET /event를 요청함
    2. 서버가 301 Moved Permanently + Location: /new-event를 응답함
    3. 브라우저가 자동으로 리다이렉트함
    4. 클라이언트가 GET /new-event를 요청함
    5. 서버가 200 OK를 응답함
- 리다이렉션의 종류
  - 영구 리다이렉션: 특정 리소스의 URI가 영구적으로 이동함(ex. /members -> /users, /event -> /new-event)
  - 일시 리다이렉션: 일시적인 변경을 의미함(ex. 주문 완료 후 주문 내역 화면으로 이동하는 PRG 패턴)
  - 특수 리다이렉션: 결과 대신 캐시를 사용함(ex. 304 Not Modified)

<br>

### 영구 리다이렉션 - 301, 308
- 리소스의 URI가 영구적으로 이동한 상태를 의미함
- 원래의 URL을 사용하지 않으며, 검색 엔진 등에서도 변경을 인지함
- 301 Moved Permanently: 리다이렉트 시 요청 메서드가 GET으로 변하고 본문이 제거될 수 있음(MAY)
  - ex. POST /event + 본문 -> 리다이렉트 후 GET /new-event, 본문 제거됨
- 308 Permanent Redirect: 301과 기능은 같으나 요청 메서드와 본문이 유지됨
  - ex. POST /event + 본문 -> 리다이렉트 후 POST /new-event, 본문 유지됨

<br>

### 일시적인 리다이렉션 - 302, 307, 303
- 리소스의 URI가 일시적으로 변경된 상태를 의미하므로, 검색 엔진 등에서 URL을 변경하면 안 됨
- 302 Found: 리다이렉트 시 요청 메서드가 GET으로 변하고 본문이 제거될 수 있음(MAY)
- 307 Temporary Redirect: 302와 기능은 같으나 요청 메서드와 본문이 유지됨(메서드 변경 금지, MUST NOT)
- 303 See Other: 302와 기능은 같으나 리다이렉트 시 요청 메서드가 반드시 GET으로 변경됨
- 무엇을 쓸 것인가
  - 처음 302 스펙의 의도는 HTTP 메서드를 유지하는 것이었으나, 웹 브라우저들이 대부분 GET으로 바꾸어버림(일부는 다르게 동작함)
  - 이에 따라 모호한 302를 대신하는 명확한 307과 303이 등장했으며, 301에 대응하는 308도 등장함
  - 307, 303을 권장하지만 이미 많은 애플리케이션 라이브러리가 302를 기본값으로 사용 중임
  - 자동 리다이렉션 시 GET으로 변해도 무방하다면 302를 사용해도 큰 문제는 없음

<br>

### PRG(Post/Redirect/Get)
- PRG 사용 전의 문제 상황
  1. POST /order로 주문하면 서버가 주문 데이터를 저장함
  2. 서버가 200 OK와 함께 주문완료 화면을 응답함
  3. 사용자가 결과 화면에서 새로고침을 수행함
  4. 새로고침이 곧 재요청이므로 POST /order가 다시 전송되어 중복 주문이 발생함
- PRG 적용 후
  1. POST /order로 주문하면 서버가 주문 데이터를 저장함
  2. 서버가 302 Found + Location: /order-result/19를 응답함
  3. 브라우저가 자동 리다이렉트하여 GET /order-result/19를 요청함
  4. 서버가 200 OK와 함께 주문완료 화면을 응답함
  5. 이후 새로고침해도 GET /order-result/19만 재요청되므로 중복 주문이 발생하지 않음
- 핵심은 POST로 주문한 후 주문 결과 화면을 GET 메서드로 리다이렉트하는 것에 있음
- URL이 이미 POST에서 GET으로 리다이렉트된 상태이므로 새로고침이 안전함

<br>

### 기타 리다이렉션 - 300, 304
- 300 Multiple Choices: 사용하지 않음
- 304 Not Modified
  - 캐시를 목적으로 사용함
  - 클라이언트에게 리소스가 수정되지 않았음을 알려주어, 클라이언트가 로컬에 저장된 캐시를 재사용하도록 함(캐시로 리다이렉트)
  - 로컬 캐시를 사용해야 하므로 304 응답에는 메시지 바디를 포함하면 안 됨
  - 조건부 GET, HEAD 요청 시 사용함
  - 상세한 내용은 [HTTP 캐시와 조건부 요청](/http/http-cache.md) 참고

<br>

### 4xx - 클라이언트 오류
- 클라이언트의 요청에 잘못된 문법 등이 있어 서버가 요청을 수행할 수 없는 상태이며, 오류의 원인이 클라이언트에 있음
- 클라이언트가 이미 잘못된 요청이나 데이터를 보내고 있으므로, 똑같이 재시도하면 계속 실패한다는 점이 중요함
- 400 Bad Request: 클라이언트가 잘못된 요청을 해서 서버가 요청을 처리할 수 없음
  - 요청 구문이나 메시지 등의 오류에 해당하며, 클라이언트는 요청 내용을 다시 검토한 후 보내야 함
  - ex. 요청 파라미터가 잘못되거나 API 스펙이 맞지 않는 경우
- 401 Unauthorized: 클라이언트가 해당 리소스에 대한 인증이 필요함
  - 401 오류 발생 시 응답에 WWW-Authenticate 헤더와 함께 인증 방법을 설명해야 함
  - 인증(Authentication)은 본인이 누구인지 확인하는 것이고(로그인), 인가(Authorization)는 권한을 부여하는 것임(ADMIN 권한처럼 특정 리소스에 접근할 수 있는 권한. 인증이 있어야 인가가 있음)
  - 이름이 Unauthorized이지만 실제 의미는 인증되지 않음이라는 점에 주의해야 함
- 403 Forbidden: 서버가 요청을 이해했지만 승인을 거부함
  - 주로 인증 자격 증명은 있으나 접근 권한이 불충분한 경우에 해당함
  - ex. 어드민 등급이 아닌 사용자가 로그인은 했지만 어드민 리소스에 접근하는 경우
- 404 Not Found: 요청 리소스를 찾을 수 없음
  - 요청 리소스가 서버에 없는 경우에 해당함
  - 클라이언트가 권한이 부족한 리소스에 접근할 때 해당 리소스의 존재를 숨기고 싶은 경우에도 사용함
- 405 Method Not Allowed: 서버에서 지원하지 않는 HTTP 메서드로 요청함
  - 응답에 허용 가능한 메서드를 담은 Allow 헤더를 포함해야 함

<br>

### 5xx - 서버 오류
- 서버 문제로 오류가 발생한 상태
- 서버에 문제가 있는 것이므로 재시도하면 성공할 수도 있음(복구되는 경우 등)
- 500 Internal Server Error: 서버 내부 문제로 오류가 발생함. 애매하면 500을 사용함
- 503 Service Unavailable: 서비스 이용이 불가능함
  - 서버가 일시적인 과부하 또는 예정된 작업으로 잠시 요청을 처리할 수 없는 상태
  - Retry-After 헤더 필드로 얼마 뒤에 복구되는지 전달할 수 있음

<br>

### 자주 쓰는 상태코드 정리
- 200 OK: 조회 및 처리 성공
- 201 Created: 리소스 생성 성공. Location 헤더를 동반함
- 204 No Content: 성공했으나 응답 바디가 없음
- 301 / 308: 영구 이동. 308은 메서드와 본문을 유지함
- 302 / 307 / 303: 일시 이동. 307은 메서드를 유지하고, 303은 GET으로 변경함
- 304 Not Modified: 캐시 재사용. 바디가 없음
- 400 Bad Request: 요청 문법 및 파라미터 오류
- 401 Unauthorized: 인증이 필요함
- 403 Forbidden: 인증은 되었으나 권한이 부족함
- 404 Not Found: 리소스가 없음
- 405 Method Not Allowed: 허용되지 않은 메서드. Allow 헤더를 동반함
- 500 Internal Server Error: 서버 내부 오류
- 503 Service Unavailable: 일시적 과부하 및 점검. Retry-After 헤더를 동반함

#### 배워가는 것들
- 상태 코드를 상위 자리 기준으로 해석하도록 설계했기 때문에 새로운 코드가 추가되어도 클라이언트를 수정할 필요가 없다는 점이 인상적이었다. 확장 가능한 스펙 설계의 좋은 예시라 생각한다
- 401과 403의 차이, 즉 인증과 인가의 차이를 명확히 구분할 수 있게 되었다. API 에러 응답을 설계할 때 이 둘을 혼동하지 않아야 한다
- PRG 패턴을 통해 새로고침으로 인한 중복 요청을 막을 수 있다는 점을 익혔다. 주문이나 결제처럼 중복이 치명적인 기능에서 반드시 고려해야 할 패턴이다
