# HTTP 기본

### HTTP(HyperText Transfer Protocol)
- 원래 HTML 문서를 전송하기 위해 출발했으나, 현재는 사실상 모든 데이터의 전송 수단으로 사용됨
- 전송 가능한 데이터
  - HTML, TEXT
  - IMAGE, 음성, 영상, 파일
  - JSON, XML(API)
  - 그 외 거의 모든 형태의 데이터
- 서버 간 데이터 통신에서도 대부분 HTTP를 사용함

<br>

### HTTP 역사
- HTTP/0.9(1991년): GET 메서드만 지원하며, HTTP 헤더가 없음
- HTTP/1.0(1996년): 메서드와 헤더가 추가됨
- HTTP/1.1(1997년): 가장 많이 사용하며, 학습의 기준이 되는 버전
  - 표준 문서 변천: RFC2068(1997) -> RFC2616(1999) -> RFC7230~7235(2014)
- HTTP/2(2015년): 성능이 개선됨
- HTTP/3(진행 중): TCP 대신 UDP를 사용하며, 성능이 개선됨
- 기반 프로토콜
  - HTTP/1.1, HTTP/2: TCP 기반
  - HTTP/3: UDP 기반
- 현재는 HTTP/1.1이 주력이며, HTTP/2와 HTTP/3의 비중이 점진적으로 증가하는 추세임

<br>

### HTTP의 4대 특징
- 클라이언트 서버 구조
- 무상태 프로토콜(Stateless), 비연결성(Connectionless)
- HTTP 메시지 기반
- 단순함, 확장 가능함

<br>

### 클라이언트 서버 구조
- 요청(Request)과 응답(Response) 구조를 가짐
- 클라이언트는 서버에 요청을 보낸 후 응답을 대기하며, 서버는 요청에 대한 결과를 만들어 응답함
- 이 구조의 의의는 관심사의 분리에 있음
  - 클라이언트는 UI/UX와 사용성에 집중함
  - 서버는 비즈니스 로직과 데이터에 집중함
  - 결과적으로 양쪽이 독립적으로 진화할 수 있음

<br>

### 무상태 프로토콜(Stateless)
- 서버가 클라이언트의 상태를 보존하지 않는 특성
  - 장점: 서버 확장성이 높음(스케일 아웃에 유리함)
  - 단점: 클라이언트가 매 요청마다 필요한 데이터를 반복 전송해야 함
- 상태 유지(Stateful)와의 비교 - 매장 응대에 비유
  - 문맥 보관: 상태 유지는 점원이 이전 대화 내용을 기억하지만, 무상태는 고객이 매 요청마다 필요한 정보를 모두 제시해야 함
  - 담당자 교체: 상태 유지는 중간에 점원이 바뀌면 상태 인계 없이는 응대가 불가능하지만, 무상태는 점원이 바뀌어도 응대 가능함
  - 확장: 상태 유지는 같은 서버를 유지해야 하므로 확장에 제약이 있지만, 무상태는 아무 서버나 호출할 수 있어 무한 증설이 가능함
  - 장애: 상태 유지는 해당 서버 장애 시 처음부터 다시 진행해야 하지만, 무상태는 다른 서버로 즉시 전달할 수 있음
- 서버 관점의 정리
  - 상태 유지의 경우, 항상 같은 서버가 유지되어야 하므로 중계 서버가 특정 서버로 고정 라우팅을 해야 함
  - 무상태의 경우, 요청에 필요한 정보가 모두 포함되어 있으므로 어느 서버로 보내도 무방함
  - 결과적으로 무상태는 수평 확장(스케일 아웃)에 매우 유리하며, 갑작스러운 트래픽 증가 시에도 서버를 대거 투입할 수 있음
- 실무에서의 한계
  - 모든 것을 무상태로 설계할 수 있는 경우와 없는 경우가 공존함
  - 무상태가 가능한 예: 로그인이 필요 없는 단순 소개 화면
  - 상태 유지가 필요한 예: 로그인. 로그인한 사용자의 상태를 서버에 유지해야 하며, 일반적으로 브라우저 쿠키와 서버 세션 등을 사용함
  - 원칙적으로 상태 유지는 최소한만 사용해야 함
- 무상태를 기억해야 하는 이유
  - 서버 개발자가 가장 어려워하는 업무는 특정 시각에 집중되는 대용량 트래픽 처리임(ex. 선착순 이벤트, 명절 KTX 예약, 수강 신청)
  - ex. 저녁 6시 선착순 1,000명 할인 이벤트에 수만 명이 동시에 요청하는 상황
  - 가급적 무상태로 설계해야 서버 증설로 대응할 수 있음

<br>

### 비연결성(Connectionless)
- 연결을 유지하는 모델의 문제
  - 클라이언트가 요청을 보내지 않는 시간에도 서버가 연결을 계속 유지해야 함
  - 유휴 연결만큼 서버 자원이 지속적으로 소모됨
- 연결을 유지하지 않는 모델
  - 요청과 응답이 끝나면 TCP/IP 연결을 종료함
  - 서버가 연결을 유지하지 않으므로 최소한의 자원만 사용함
- HTTP는 기본적으로 연결을 유지하지 않는 모델을 전제로 함
  - 일반적으로 초 단위 이하의 빠른 속도로 응답이 완료됨
  - 1시간 동안 수천 명이 사용해도 실제 서버가 동시에 처리하는 요청은 수십 개 이하로 매우 적음(ex. 웹 브라우저에서 검색 버튼을 연속으로 계속 누르지는 않음)
  - 결과적으로 서버 자원을 매우 효율적으로 사용할 수 있음
- 한계와 극복
  - 연결 재수립 비용: 요청마다 TCP/IP 연결을 새로 맺어야 하므로 3 way handshake 시간이 추가됨
  - 자원 다량 요청: HTML뿐만 아니라 자바스크립트, CSS, 이미지 등 수많은 자원을 함께 다운로드해야 함
  - 극복 방법으로 HTTP 지속 연결(Persistent Connections)을 사용함
    - 초기 방식: 자원 하나마다 연결 -> 요청/응답 -> 종료를 반복함
    - 지속 연결: 한 번 연결한 후 필요한 자원을 모두 주고받고 종료함
  - HTTP/2, HTTP/3에서 추가적인 최적화가 이루어지고 있음

<br>

### HTTP 메시지 구조
- 시작 라인(start-line) - 헤더(header) - 공백 라인(empty line, CRLF) - 메시지 바디(message body) 형태로 구성됨
- 공식 스펙(RFC 7230)
```
HTTP-message = start-line
               *( header-field CRLF )
               CRLF
               [ message-body ]
```
- 요청 메시지도 body 본문을 가질 수 있음
- 시작 라인 - 요청 메시지
```
request-line = method SP request-target SP HTTP-version CRLF
```
```http
GET /search?q=hello&hl=ko HTTP/1.1
Host: www.google.com
```
  - HTTP 메서드: 서버가 수행해야 할 동작을 지정함(ex. GET은 조회, POST는 요청 내역 처리)
  - 요청 대상: absolute-path[?query] 형태이며, /로 시작하는 절대경로를 사용함
  - HTTP 버전: 프로토콜 버전을 의미함
  - 참고로 `*`, `http://...?x=y`와 같은 다른 유형의 경로 지정 방법도 존재함
- 시작 라인 - 응답 메시지
```
status-line = HTTP-version SP status-code SP reason-phrase CRLF
```
```http
HTTP/1.1 200 OK
```
  - HTTP 버전, HTTP 상태 코드, 이유 문구로 구성됨
  - HTTP 상태 코드는 요청의 성공/실패를 표현함(ex. 200 성공, 400 클라이언트 오류, 500 서버 내부 오류)
  - 이유 문구는 사람이 이해할 수 있는 짧은 상태 코드 설명 글임
- HTTP 헤더
```
header-field = field-name ":" OWS field-value OWS
```
  - OWS는 띄어쓰기 허용을 의미하며, field-name은 대소문자를 구분하지 않음
  - HTTP 전송에 필요한 모든 부가정보를 담음(ex. 메시지 바디의 내용, 크기, 압축, 인증, 요청 클라이언트 정보, 서버 애플리케이션 정보, 캐시 관리 정보 등)
  - 표준 헤더가 매우 많으며, 필요 시 임의의 헤더를 추가할 수도 있음
- HTTP 메시지 바디
  - 실제 전송할 데이터가 들어감
  - HTML 문서, 이미지, 영상, JSON 등 byte로 표현할 수 있는 모든 데이터를 전송할 수 있음

<br>

### 단순함, 확장 가능
- HTTP는 스펙 자체가 단순하며, 메시지 구조도 매우 단순함
- 크게 성공하는 표준 기술의 공통점은 단순하면서 확장 가능하다는 점에 있음

#### 배워가는 것들
- 무상태와 비연결성이 단순한 특징이 아니라 HTTP 확장성의 근원이라는 점을 익힐 수 있었다. 대용량 트래픽 대응을 고려한다면 상태 유지는 최소한으로 가져가야 한다는 기준을 세울 수 있었다
- HTTP 메시지가 시작 라인, 헤더, 공백 라인, 바디라는 매우 단순한 구조로 되어있음에도 지금까지 확장되며 쓰이고 있다는 점에서, 단순함이 곧 확장성의 조건이 될 수 있다는 것을 느꼈다
