# 스키마 마이그레이션(Schema Migration)

### 스키마 마이그레이션
- 데이터베이스의 구조(테이블, 컬럼, 인덱스, 제약조건 등) 변경을 버전이 매겨진 스크립트로 관리하는 방식
  - 소스 코드를 Git으로 관리하듯이, 스키마 변경 이력도 코드와 함께 관리함
  - 어느 환경(로컬, 개발, 운영)이든 같은 스크립트를 같은 순서로 적용하므로, 환경마다 스키마가 달라지는 문제를 방지할 수 있음
- 사람이 직접 DDL을 실행하는 방식의 문제점
  - 어떤 변경이 어느 환경에 적용되었는지 알기 어려움
  - 변경 순서가 어긋나거나 일부 환경에 누락되기 쉬움
  - 변경 이력이 남지 않아, 장애가 발생했을 때 원인을 추적하기 어려움
- Java 진영에서는 Flyway와 Liquibase가 대표적인 마이그레이션 도구임
  - Flyway: SQL 파일을 그대로 작성하는 방식이라 학습 비용이 낮음
  - Liquibase: XML, YAML, JSON 등으로 변경 내용을 추상화하여 작성할 수 있으며, 여러 DBMS를 동시에 지원해야 할 때 유리함

<br>

### ddl-auto와 마이그레이션 도구
- spring.jpa.hibernate.ddl-auto는 Hibernate가 엔티티를 보고 스키마를 어떻게 다룰지 지정하는 속성
  - none: 아무것도 하지 않음
  - validate: 엔티티와 테이블이 일치하는지 검증만 수행하며, 불일치 시 애플리케이션 기동이 실패함
  - update: 엔티티와 비교하여 부족한 테이블과 컬럼을 추가함
  - create: 기동 시 기존 테이블을 삭제한 후 새로 생성함
  - create-drop: create와 동일하며, 종료 시 테이블을 삭제함
- 기본값은 내장 DB(H2 등)를 사용하면서 마이그레이션 도구가 없는 경우 create-drop, 그 외에는 none임
- update를 운영 환경에서 사용하면 안 되는 이유
  - 컬럼 추가만 수행하고, 컬럼 삭제나 타입 변경은 반영하지 않으므로 엔티티와 테이블이 조용히 어긋남
  - 데이터가 있는 테이블에 NOT NULL 컬럼을 추가하지 못함
  - 어떤 변경이 언제 일어났는지 이력이 남지 않음
  - 애플리케이션이 DDL 권한을 가져야 하므로, 여러 서비스가 공유하는 DB에서는 위험함
- 따라서 스키마 변경은 마이그레이션 도구로만 수행하고, ddl-auto는 validate로 두는 조합이 권장됨
  - 엔티티만 수정하고 마이그레이션 스크립트를 빠뜨리면 기동 시점에 바로 실패하므로, 실수를 일찍 발견할 수 있음
```
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

### Flyway
- SQL 스크립트 기반의 데이터베이스 마이그레이션 도구
- 애플리케이션이 기동될 때 아직 적용되지 않은 스크립트를 버전 순서대로 실행함
- 적용 이력은 flyway_schema_history 테이블에 기록됨
  - 스크립트의 버전, 설명, 체크섬(Checksum), 적용 시각, 성공 여부 등이 저장됨
- Spring Boot 4.x부터는 spring-boot-starter-flyway를 추가하며, PostgreSQL 등 일부 DBMS는 별도의 Flyway 모듈을 함께 추가해야 함
```
build.gradle

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-flyway'
    runtimeOnly 'org.flywaydb:flyway-database-postgresql'
}
```
- Spring Boot는 Flyway 마이그레이션이 끝난 뒤에 JPA(EntityManagerFactory)를 초기화하므로, ddl-auto: validate는 마이그레이션이 적용된 스키마를 대상으로 검증됨

<br>

### 마이그레이션 파일 작성 규칙
- 기본 위치는 src/main/resources/db/migration이며, 파일 이름 규칙에 따라 종류가 구분됨
  - V{버전}__{설명}.sql: 버전 마이그레이션. 한 번만 적용되며, 버전 순서대로 실행됨
  - R__{설명}.sql: 반복 마이그레이션. 내용(체크섬)이 바뀔 때마다 다시 적용되며, View나 함수 정의에 사용함
  - 버전과 설명 사이에는 밑줄(_)이 두 개 들어감
```
db/migration
 ├─ V1__init.sql
 ├─ V2__add_soft_delete.sql
 └─ V3__add_environment_secrets.sql
```
- 이미 적용된 파일은 수정하면 안 됨
  - Flyway는 기동 시 적용된 파일의 체크섬을 다시 계산하여 비교하며, 다르면 기동을 거부함
  - 변경이 필요하면 수정하지 않고, 새 버전의 파일을 추가해야 함
- 무료 버전(Community)은 되돌리기(Undo) 마이그레이션을 지원하지 않으므로, 잘못 적용된 변경도 새 버전의 파일로 바로잡음
- 스키마 이름을 SQL에 직접 적지 않고, 설정으로 지정할 수 있음
  - schemas: 관리할 스키마 목록. 존재하지 않으면 Flyway가 생성함
  - default-schema: 스키마를 생략한 테이블과 flyway_schema_history가 생성될 스키마
```
spring:
  flyway:
    schemas: sentinel
    default-schema: sentinel
```

### 데이터가 있는 테이블을 변경할 때 유의사항
- NOT NULL 컬럼을 추가할 때는 DEFAULT를 지정하거나, 컬럼을 추가하고 값을 채운 뒤 제약조건을 추가해야 함
```
ALTER TABLE test_result ADD COLUMN retry_count INTEGER DEFAULT 0 NOT NULL;
```
- PostgreSQL 11부터는 상수 DEFAULT를 가진 컬럼 추가 시 기존 행을 다시 쓰지 않으므로, 데이터 양과 무관하게 빠르게 적용됨
  - 반면 기존 행의 값을 모두 갱신하는 마이그레이션은 행 수에 비례하여 오래 걸리며, 그동안 테이블에 잠금이 걸릴 수 있음
  - 큰 테이블을 변경하는 마이그레이션은 운영 규모에 가까운 데이터로 적용 시간을 미리 확인하는 것이 좋음
- PostgreSQL은 DDL도 트랜잭션 안에서 실행되므로, 마이그레이션 도중 실패하면 해당 파일의 변경 전체가 롤백됨
  - MySQL 등 DDL이 자동 커밋되는 DBMS에서는 실패한 지점까지의 변경이 남으므로, 파일 하나에 하나의 변경만 담는 것이 안전함

<br>

### 표준 SQL로 작성하기
- 마이그레이션 스크립트는 특정 DBMS 전용 문법 대신 ANSI SQL 표준 문법으로 작성하면, DBMS를 바꾸거나 여러 DBMS를 지원할 때 수정할 부분이 줄어듦
  - PostgreSQL 전용 문법 예시: ::(타입 캐스트), now(), RETURNING, ON CONFLICT
  - 표준 문법 예시: CAST(... AS ...), CURRENT_TIMESTAMP, GENERATED BY DEFAULT AS IDENTITY, TIMESTAMP WITH TIME ZONE
- 표준 예약어(POSITION, METHOD, TRIGGER 등)는 컬럼명으로 사용하지 않는 것이 좋음
  - DBMS에 따라 따옴표로 감싸야만 사용할 수 있어, 쿼리 작성 시 실수가 생기기 쉬움
- CREATE INDEX처럼 표준에 정의되지 않았지만 주요 DBMS에서 공통으로 쓰이는 구문은 예외로 허용함
- 여러 서비스가 공유하는 DB라면, 애플리케이션 전용 스키마와 그 스키마에만 권한을 가진 계정을 사용하는 것이 좋음
```
CREATE SCHEMA sentinel;
CREATE USER sentinel_app WITH PASSWORD '...';
GRANT USAGE, CREATE ON SCHEMA sentinel TO sentinel_app;
```

#### 배워가는 것들
- 개발할 때 편하게 쓰던 ddl-auto: update가 운영에서는 조용한 불일치를 만든다는 것을 알게 되었다. 스키마 변경은 마이그레이션 도구에 맡기고 ddl-auto는 검증 용도로만 쓰는 조합이 실수를 가장 빨리 드러낸다.
- 이미 적용된 마이그레이션 파일을 고치면 체크섬 불일치로 기동이 거부된다는 점이 인상적이었다. 스키마 이력도 코드처럼 되돌리지 않고 앞으로만 쌓아가야 한다.
- 같은 컬럼 추가라도 DEFAULT 유무와 DBMS 버전에 따라 적용 시간이 크게 달라질 수 있다는 것을 알게 되었다. 큰 테이블을 다루는 마이그레이션은 실제 규모의 데이터로 미리 확인하는 습관을 들여야겠다.
